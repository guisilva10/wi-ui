# Story 1.3 — Registry API

## Descricao

Como CLI, quero consumir API que serve metadados e codigo dos componentes, para resolver e copiar componentes pro projeto do usuario.

## Status: Pending

## Endpoints

- `GET /api/registry/list` — lista todos componentes (name, category, description)
- `GET /api/registry/[name]` — retorna componente completo (code, deps, files)
- `GET /api/registry/[name]/meta` — retorna so metadata
- `GET /api/registry/diff/[name]` — retorna diff entre versoes

## Criterios de Aceite

- [ ] API Routes implementadas em `src/app/api/registry/`
- [ ] Feature `registry/` implementada (domain → infrastructure)
- [ ] Endpoint list retorna todos componentes
- [ ] Endpoint [name] retorna codigo + deps + files
- [ ] Rate limiting basico (100 req/min por IP)
- [ ] Cache headers corretos (CDN friendly)
- [ ] Resposta JSON tipada
- [ ] Fallback gracioso se componente nao existe (404)

## Tarefas Tecnicas

1. Implementar feature `registry/`:
   - domain: RegistryEntry entity, ComponentMeta VO, RegistryRepository interface
   - application: ListComponentsUseCase, GetComponentUseCase, DiffComponentUseCase
   - infrastructure: FileSystemRegistryRepository (le de packages/registry/)
2. Criar API Routes:
   - `src/app/api/registry/list/route.ts`
   - `src/app/api/registry/[name]/route.ts`
   - `src/app/api/registry/[name]/meta/route.ts`
   - `src/app/api/registry/diff/[name]/route.ts`
3. Implementar FileSystemRegistryRepository:
   - Le componentes de `packages/registry/`
   - Parse meta.json
   - Le source files
   - Resolve deps entre componentes
4. Adicionar rate limiting (middleware ou next-rate-limit)
5. Configurar cache headers (stale-while-revalidate)
6. Testes unitarios dos use cases
7. Testes integracao dos endpoints

## Dependencias

- Story 0.2 (estrutura)
- Story 1.1 (componentes existem no registry)

- Em prod: pode cachear em KV/Redis ou pre-build JSON
